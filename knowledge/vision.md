# Vision

> Материализованное видение проекта: единая картина, к которой сверяется каждая
> новая задача. Живой документ — синхронизируется вместе с решениями (см.
> [Порядок обновления](#порядок-обновления)). Это НЕ архив решений (он в
> `knowledge/decisions.md`), а его дистиллят: что строим, где мы сейчас, куда
> идём и что осознанно НЕ делаем.

## Что строим

**Hermes Agent** — самоулучшающийся AI-агент (Nous Research): движок с
встроенной петлёй обучения (создаёт навыки из опыта, ищет по прошлым сессиям,
строит модель пользователя), который живёт не на ноутбуке, а на дешёвом VPS /
serverless и доступен из любого мессенджера через единый gateway. Любая модель,
любой провайдер, без вендор-лока.

Поверх движка — **автономная оркестрация** (Zeus-слой): kanban-доска, по которой
агент ведёт проекты сам, с минимальным надзором оператора. Задача проходит путь
`triage → todo → ready → running → done`; регулярные процессы (крон-«регулярные»)
следят за здоровьем, безопасностью, целостностью и дрейфом. Оператор задаёт
направление и отвечает на КОРОТКИЕ вопросы-решения, а не нянчит каждый шаг.

## Текущие фичи

- **Kanban-оркестрация**: колонки triage→todo→ready→running→done, диспетчер,
  воркспейсы (scratch / repo / worktree), пакетное взятие с планировщиком.
- **Гейт triage→todo** (specifier): раскрывает одну строку в конкретный спек и
  промоутит в todo. Теперь ещё и **vision-проверка** — задача, не вписывающаяся в
  эту картину, не уезжает в todo автоматически (см.
  `hermes_cli/kanban_specify.py`).
- **Проблемы (Ось-B)**: единый findings-store (`zeus.db`), куда пишут регулярные
  сканеры (reflection / advisor / security-review / integrity / regular-crons /
  **vision-сверка**). Оператор принимает (→ карточка triage) или отклоняет.
- **Регулярные процессы**: security-review (sealed-core), integrity-agent
  (kanban↔git сверка деливери), regular-crons (аномалии кронов),
  **vision-reconcile** (сверка бэклога с этим документом).
- **Sealed-core / userland** со свитчом self-modify; двухслойный backup/restore.
- **Многоканальность**: Telegram/Discord/Slack/WhatsApp/Signal/CLI из одного
  gateway; служебный канал инбокса решений.
- **Токен-учёт и пейсинг** (zeus-леджер), shadow-прайсы, бюджеты телеметрии.
- **Провайдеры и модели**: `hermes model`, вспомогательные (auxiliary) задачи с
  собственным дешёвым/планировщик-класса роутингом.

## Куда идём

- Оператор нянчит меньше: то, что раньше делалось руками по ночам (проверка
  деливери, сверка бэклога с видением, гейт triage→todo), становится
  регулярными процессами. **Продукт поглощает няньку.**
- Гейт triage→todo сверяется с этим документом на модели планировщик-класса
  (Fable) без ручного ночного надзора.
- Периодическая сверка бэклога с видением ловит дрейф — задачи-сироты и
  противоречия — и складывает находки в Проблемы.
- Standalone-продукт поверх Hermes: свой UI и установочный набор (движок +
  память + observability + UI), дефолты поставки отличаются от дефолтов Hermes
  (напр. `kanban.auto_decompose=false`).

## Что НЕ делаем

- **Не полурешения.** «Локальный репозиторий и всё», «MVP, который ничего не
  доводит до конца» — анти-паттерн. Фича доводится до рабочего состояния, а не
  бросается на середине.
- **Не форкаем Hermes-движок ради расширений** — расширения кладутся в
  `~/.hermes/plugins/`, чтобы обновления движка их не трогали.
- **Не включаем auto_decompose по умолчанию** — декомпозиция только явная
  (инцидент 2026-07-16: авто-декомпозиция сожгла ~25% дневного бюджета).
- **Не просим оператора проверять/принимать работу** — воркер тестирует сам
  (сборка, тесты, живой прогон) и завершает; оператор скажет постфактум.
- **Не задаём технических микро-вопросов** оператору — только продуктовые
  решения (что видит пользователь, какие данные/фичи важны).
- **Не Postgres / не мультиарендность** пока нет облачного мультипользования —
  SQLite в стиле самого Hermes.

## Порядок обновления

Этот документ — дистиллят решений, а не их источник. Он синхронизируется, чтобы
гейт и сверка работали на актуальной картине:

1. **Источники** (только читаются, не переписываются): `knowledge/decisions.md`
   (реестр принятых решений), `knowledge/open-decisions.md` (открытые вопросы) и
   ночные операторские решения (kanban steer / логи доски).
2. **Когда обновлять**: при принятии нового решения, меняющего картину (новая
   фича в «Текущие фичи», смена направления в «Куда идём», новый запрет в «Что НЕ
   делаем»). Правка — точечная, в соответствующий раздел; шапку `updated:`
   двигаем на дату правки.
3. **Кто читает**: гейт triage→todo (`hermes_cli/kanban_specify.py`) подмешивает
   этот файл в контекст планировщика на каждой спецификации; регулярная сверка
   (`hermes_cli/vision_reconcile.py`) измеряет по нему дрейф бэклога.
4. **Резолвинг файла**: по умолчанию `<repo>/knowledge/vision.md`; переопределяется
   `HERMES_VISION_DOC` (явный путь) или `HERMES_PROJECT_ROOT/knowledge/vision.md`.
5. **Модель гейта**: vision-проверку выполняет вспомогательная задача
   `triage_specifier` — направьте её на модель планировщик-класса (Fable) через
   `hermes model` → auxiliary → Triage specifier, чтобы суждение о вписываемости
   было качественным.
